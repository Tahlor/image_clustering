# Physical Document Duplicate/Occlusion Review Tool

> **Canonical agent entry point.** When a task says to “review” clustered document images, inspect this file first. In this repository, “the review tool” means the standalone `image-review` application described here—not Vantage2, not the field-extraction review route, not the generated static HTML bundle, and not a generic image viewer.

## Identity

**Name:** Physical Document Duplicate/Occlusion Review Tool  
**Command:** `image-review`  
**Repository:** this independent `image_clustering` checkout  
**Source:** `src/image_clustering/review/`  
**Primary use:** human review of automatically grouped captures of the same physical document scene, including changing physical occlusions, near-duplicates, cluster membership, and proposed crop boxes.

The tool exists to answer: **“Do these captures belong to the same physical document scene, and are the proposed page/foreground-sheet boxes usable?”** It does not perform OCR or field comparison, and it is not a hosted service.

## Do not route this task elsewhere

| Surface | Boundary |
| --- | --- |
| `image-review` | **This tool:** interactive cluster membership, occlusion, and crop-box review with durable local decisions. |
| `output_root/review/index.html` | Static diagnostic review generated by `scripts/evaluate_dataset.py`; browser-local labels are separate and are not the interactive server’s durable state. |
| Vantage2 review/import routes | Downstream product review/import; not a replacement for this clustering review surface. |
| Field-extraction or Gemini batch artifacts | Extraction results; they are not clustering-review inputs. |
| `scripts/review_clusters.py` | Compatibility wrapper only. Use `image-review` in new commands and documentation. |

## The one correct launch contract

The argument is a **completed image-clustering evaluation output root**:

```text
<output_root>/
└── clustering/
    └── clustering.json       # required
```

Recommended additional inputs:

```text
<output_root>/
├── inventory/dataset_inventory.json        # source dimensions
├── reports/crops_for_recognizer.jsonl     # proposed crop boxes, when produced
├── cropping.json                           # cropper result, when produced
└── review_labels/                           # created/used by the interactive tool
```

Referenced source images must remain readable at the paths recorded in `clustering/clustering.json`. The server only serves previews for source images that belong to the loaded run.

### Preferred command

From this repository root, after an editable install:

```bash
python -m pip install -e .
image-review --output_dir /path/to/completed-evaluation
```

On Windows PowerShell, the same command is valid on one line:

```powershell
image-review --output_dir "C:\path\to\completed-evaluation"
```

The server opens the default browser and logs the actual URL. Defaults are:

- host: `127.0.0.1`;
- port: `8756`;
- browser: opened automatically.

If the console script is unavailable but the package source is present, use the module entry point with the active Python environment:

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) "src")
python -m image_clustering.review.cli --output_dir "C:\path\to\completed-evaluation"
```

Use `--no_browser` when launching from an agent or another context where opening a browser is undesirable; report the URL instead:

```bash
image-review --output_dir /path/to/completed-evaluation --no_browser
```

## Never restart a running review instance blindly

Before launching, check whether the default server is already running:

```powershell
netstat -ano | findstr :8756
```

If `127.0.0.1:8756` is already listening, **use the existing URL and do not kill or replace the process**. A port check that is temporarily inconclusive is not permission to start competing copies or delete review state. Only launch a new instance when the existing server has been verified absent, or choose an explicitly different port with `--port`.

After launching, verify the application rather than trusting a process-start message:

1. `GET http://127.0.0.1:8756/` returns `200` HTML.
2. `GET http://127.0.0.1:8756/api/dataset` returns the loaded cluster dataset.
3. A preview request for a source path from that dataset returns `200 image/jpeg`.

A live server can take time to parse a large `clustering.json` before it begins listening. Do not start a second loader during that interval.

## What review state means

The server reads canonical clustering/crop artifacts but does not rewrite them. It autosaves reviewer decisions to:

```text
<output_root>/review_labels/decisions.json
```

The **Export corrected manifests** action writes derived files under the same directory, including corrected cluster membership, reviewed crop boxes, irregular exclusions, a summary, and an export manifest. Decisions and exports are durable local review evidence; they do not prove that the underlying clustering or crop algorithm is correct.

### Current subtype boundary: model evidence vs. review designation

The clustering model already distinguishes the two same-document cases at the **pair** level:

- `near_duplicate` means near-exact document-specific ink agreement: the same physical document was captured again with essentially the same visible content.
- `physical_occlusion` means a large, contiguous physical occlusion explains the difference while the visible area outside it agrees nearly exactly. Multiple captures can therefore provide complementary views of the same physical document scene.

The recall-first candidate scorer also exposes `same_clean_probability` and `same_occluded_probability` (the clean/non-occluded and partially occluded same-document probabilities). The reviewed evaluation labels use the corresponding `same_document_near_duplicate` and `same_document_occlusion` relations. The current physical-occlusion gate is deliberately narrower than generic visual similarity: same printed form or nearby documents are not enough, and the accepted branch requires contiguous occlusion evidence plus outside agreement.

Those are pair-level model and calibration signals, not an accepted-cluster review designation. The interactive review tool records membership as a cluster `status` (`unreviewed`, `approved`, `edited`, `dissolved`, `irregular`) and, separately, two reviewer designations:

- `relation` — what the captures share:
  - `same_document` (key `s`): literally the same visible document, re-captured or with/without a covering sheet;
  - `same_background_document` (key `g`): the same underlying base page, but a different foreground sheet on top;
  - `different_document` (key `n`);
  - `unsure` (key `u`).
  Setting a relation also sets the status it implies (same-* → `approved`, different → `dissolved`, unsure → `irregular`). A later status change that contradicts the relation (for example `a`/`d`/`i`) clears it; membership edits on a confirmed cluster keep a same-* relation. `null` means the relation was never set, which is true of every decision recorded before this field existed.
- `primary_view` — which capture is the primary unoccluded view of the (background) document: a member `image_id` (key `p` on the focused capture), `"none"` when no capture shows it unoccluded (key `o`), or `null` when not reviewed. It is independent of status.

Boxes carry a `kind`, which is drawn in its own colour: `base_page` is the page of interest (green), and
`data_bearing_overlay` is the covering or foreground sheet (red). Every box shows its eight resize handles by
default: drag a handle to resize, or drag the box body to move it, with no mode needed. A click without a drag only
selects, so it saves nothing. Drawing a new box needs draw mode (`e`); the first box drawn on a capture is a page
and later ones are occluders. `t` flips the selected box between the two kinds. Kinds are stored with the boxes in
`decisions.json` and the exports.

A proposal row in `reports/crops_for_recognizer.jsonl` may carry a `polygon` (`[[x, y], ...]` in source pixels,
for example a SAM segmentation). It is drawn as a dashed outline while its box is unchanged. Editing the box drops
the outline, because it no longer matches.

Both fields are in `decisions.json`, the corrected cluster manifest, and `review_summary.csv`. The status filter has "confirmed, relation not set" and "confirmed, primary view not set" queues for completing a pass. Do not infer a relation from `approved` alone, from crop completeness, or from form-template similarity; a cluster with `relation: null` has no reviewer subtype.

The normal review order is:

1. start with the weakest-confidence clusters;
2. inspect the full capture sequence and physical-document continuity;
3. approve, dissolve, mark irregular, or reopen cluster membership;
4. independently inspect and approve/edit crop boxes;
5. export corrected manifests only after the relevant queue has been reviewed;
6. preserve the decision provenance and counts.

The UI defaults to clusters with at least two captures and confidence-ascending order. A single-image remainder is not treated as a cluster.

## If previews are broken

Broken image links are a **source-path/input problem**, not a reason to edit the clustering JSON by hand. Check, in order:

1. the server was launched with the intended `<output_root>`;
2. `clustering/clustering.json` exists under that root;
3. a source path from `/api/dataset` exists and is readable on this machine;
4. the source path belongs to the loaded run rather than a stale copied artifact;
5. the server log and `/preview` response for the exact URL.

If source images moved, regenerate or repair the evaluation artifact through the pipeline that owns the source-path manifest. Do not silently substitute a different image directory: that can make review labels refer to the wrong captures.
